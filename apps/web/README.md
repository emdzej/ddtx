# @ddtx/web

Browse the ECU database and render its screens in the browser. Demo mode only —
nothing here talks to a vehicle yet.

## Running it

From the repo root, with `data/ecu.zip` in place:

```sh
pnpm install
pnpm build
pnpm dev
```

`pnpm dev` splits the database first if it needs to, then starts Vite. The split
writes ~1.2 GB to `data/tree` and takes about 19 s; subsequent runs compare the
archive's hash against the tree's manifest and skip it in under a second.
`pnpm db:split:force` re-splits unconditionally.

`vite.config.ts` serves `data/tree` at `/db` in development — no env var needed.
`DDTX_DB_TREE` overrides the location. In production `/db` is a static tree on
whatever host serves the app and the client code is identical; point it elsewhere
with `VITE_DB_URL`.

## Demo mode

Values come from the database, not a car. The three fill modes trade fidelity
against usefulness:

| Mode | What you get |
|---|---|
| Stored replies only | Exactly what the Qt app's demo mode shows. 94.4% of requests have a canned reply, but 11.7% are shorter than their own `minbytes`, so a lot of fields read NO DATA |
| Stored, padded *(default)* | Canned replies extended with generated bytes so every field decodes |
| All generated | Everything generated. Useful for seeing how long values get in a box the database sized for French |

Generated bytes are deterministic — a screen looks the same on every read rather
than flickering. **Vary values** opts into drift when you want to watch a refresh
actually change something.

## Finding an ECU

Vehicle is the only search field, and it is a combobox rather than a `<select>`:
139 vehicles is past the point where native type-ahead helps, since that only
matches from the first character and "megane" would find nothing under "Renault
Megane II". It matches the project code too, so `x84` works as well as `Megane II`.

Choosing a vehicle narrows Group to the systems that car actually has, and clears
a group the new vehicle doesn't have rather than silently returning nothing.

Vehicles are labelled with the model name from DDT4All's `resources/projects.json`
(see `tools/reference/gen-projects.py`); the project code stays the value, because
that is what the index matches on.

The catalogue collapses to a rail once you've chosen — worth 248px to the canvas —
and remembers that across reloads.

## Reading a screen

Screens are fixed VB canvases in twips and nothing reflows; the absolute
positions are the design. **Zoom** defaults to 100%, which is `uiscale = 8` — the
Qt app's own default — and the stage scrolls. Fit-width is available but shrinks
below native, at which point captions the database sized to just fit start
wrapping.

**Inspect layout** outlines widget bounds, marks inputs in vermilion, and shows
the caption/value split. Useful for checking geometry against the original.

Value cells carry their status: red for NO DATA (the response was too short),
yellow for a rejected request with its NRC, black for a link failure.

## What's deliberately missing

Writing to inputs, DTC read/clear, and the vehicle scan all wait on the ELM327
driver. Buttons fire their requests and the trace shows them, but in demo mode
the reply is canned either way.
